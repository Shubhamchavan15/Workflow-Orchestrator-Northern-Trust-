DAG — Directed Acyclic Graph Execution
Tasks execute in dependency order. Shipping and Notification run in parallel threads after payment succeeds, cutting total execution time. If any task fails, the engine stops, raises an alert, and sends a failure notification — no downstream tasks run.
State Machine
Every Task Goes Through These States
⏳ PENDING
Task is queued. Waiting for its upstream dependency to complete before execution begins.
🔄 RUNNING
HTTP call dispatched to the microservice. Awaiting response. Visible live on the dashboard.
✅ COMPLETED
Service returned success=true. Result stored. Next task(s) in the DAG are triggered.
❌ FAILED
All retry attempts exhausted or business failure received. Alert raised. Failure email sent.
Resilience
Exponential Backoff Retry Engine
How Retries Work
When a microservice call fails due to a network error (timeout, connection refused), the RetryManager automatically retries with increasing delays.

Business failures (card declined, out of stock) are never retried — they are definitive answers that skip straight to the alert flow.

Failure Handling
What Happens When a Task Fails
💥
Task Fails
Payment declined, inventory out of stock, or network error after all retries. Engine catches the exception immediately.
🚨
Alert Created
Critical alert written to alerts.json with order ID, customer, amount, failure reason, and timestamp. Visible instantly on Admin Dashboard.
📧
Emails Sent
Customer receives failure notification. Admin email (configured in Settings) receives full alert with order details. Both sent via Gmail SMTP.
💳 Payment Failure Scenarios
● Card declined — insufficient funds
● Card declined — suspected fraud
● Payment gateway timeout
● Invalid card number
● High-value order — manual approval needed
📦 Inventory Failure Scenarios
● Item out of stock
● Insufficient quantity available
● Back-order triggered
● Payment NOT charged (inventory checked first)
● Customer notified immediately
